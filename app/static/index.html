    Guide

    How this app works

    A knowledge graph of FortiSOAR automation: playbooks, the collections and solution packs they ship in, the connectors they call, and the documentation around them, which you can explore visually and question in plain English.

    1. What the app is

    FortiSOAR playbooks are JSON workflows: a trigger, a chain of steps, branches, approvals, calls to other playbooks, and calls to connectors (integrations with products such as FortiGate, VirusTotal or ServiceNow). Reading that JSON is slow, and the relationships between playbooks, connectors and docs are invisible in the files themselves.

    This app parses that content into a graph (stored in Neo4j) where every playbook, step, connector, collection, solution pack and document is a node and every relationship (contains, calls, uses, documented by…) is an edge. On top of the graph it offers:

    • Home: an animated map of the whole ecosystem or of all playbooks.
    • Catalog: searchable tables of every solution pack, playbook, collection, connector and document, with full detail pages that link to each other.
    • Chat: ask questions in plain English. Answers are built only from the graph and cite their sources.
    • Graph panel and diagrams: per-playbook graphs, step-by-step animation, flowcharts and sequence diagrams.

    The approach is Graph RAG (retrieval-augmented generation over a graph): search finds the relevant nodes, the graph supplies their context (steps, callers, connectors, docs), and a language model writes the answer from that context only.

    3. Where the data comes from

    All content comes from the public GitHub organisation github.com/fortinet-fortisoar. Fortinet's product documentation site (docs.fortinet.com) is deliberately not used.

    How it is fetched (scripts/fetch_fortinet.py)

    1. Repo list: the GitHub REST API lists every public repo in the org (one call per 100 repos), cached in data/fortinet/repos.jsonl.
    2. Download: each repo whose name starts with connector-, solution-, widget- or ai- is downloaded as a tarball from codeload.github.com (not rate-limited like the API).
    3. Keep only content: from each tarball only info.json, README.md, release_notes.md, docs/*.md, collection.metadata.json and playbook JSON under playbooks/ are written to data/fortinet/github/<repo>/. Code, images and CI files are skipped, and paths are checked so nothing is written outside that folder.
    4. Release-branch fallback: many repos keep their content only on release/x.y.z branches with an empty default branch. For those, branches are listed with git ls-remote and the newest release branch is fetched instead.
    5. Re-sync: re-running skips repos whose last push date hasn't changed, so only updated repos are downloaded.

    What each kind of repo contributes

    Repo kindFiles usedBecomes
    solution-pack-*, ai-*info.json (label, version, category, dependencies), playbooks/<collection>/<playbook>.json (Content Hub layout, one playbook per file) and collection.metadata.json, README.md and docs/setup.md, usage.md, contents.mdSolutionPack, PlaybookCollection, Playbook and Step nodes, plus pack documents
    connector-*<name>/info.json (configuration fields and every action with description and parameters), playbooks/playbooks.json (sample playbooks), release_notes.mdConnector and ConnectorOperation nodes, sample collections, and a generated connector reference document
    widget-*info.json, README.mdWidget documents (no playbooks)
    Some solution packs publish only a README on GitHub; their playbooks are distributed through FortiSOAR's Content Hub, so the app can only include their documentation.

    5. How the graph is built

    Everything below is deterministic code; no language model is involved in building the graph.

    5.1 Parsing playbooks

    • Both export shapes are read: Content Hub (one playbook object per file, with the collection taken from collection.metadata.json) and collection exports ({"type": "workflow_collections", "data": [{"workflows": [...]}]}).
    • Collections that reuse generic names (e.g. "03 - Triage") are prefixed with their pack: Incident Response · 03 - Triage.
    • Steps are ordered by walking the routes breadth-first from the trigger step. A route's label (e.g. "Malicious", "Approve") becomes the branch label; its name ("A -> B") is ignored.
    • A step whose arguments contain workflowReference becomes a CALLS edge to the child playbook. If that playbook isn't loaded, a placeholder node keeps the edge.
    • If the same playbook (same UUID) ships in several packs, the solution-pack copy is kept over a connector's sample copy.

    5.2 Step types

    Exports only carry an opaque step-type ID, so each step's kind is inferred from its arguments:

    5.3 Triggers

    The trigger step's arguments decide the trigger type: manual (a button on records: route/executeButtonText), record_event (on create/update of a module, with field filters), api_endpoint (custom API route with auth methods) or referenced (only started by other playbooks). The modules involved (alerts, incidents…) become TRIGGERED_ON edges.

    5.4 Scrubbing and secret detection

    Before anything is stored or embedded, text and step arguments are scrubbed: IP addresses, emails, credentials inside URLs, AWS key IDs and account IDs in ARNs, bearer tokens and long opaque strings are masked, plus any terms listed in SCRUB_TERMS. Values under credential-type keys (password, token, api_key…) are replaced with <REDACTED> when they are literal strings; {{vars…}} references, booleans and numbers are left alone. A step is flagged has_secret only when a literal credential was found, which is what the ⚠ markers in the Catalog mean.

    5.5 Connectors, solution packs and documents

    • Connectors get their label, version, category, publisher, description and online-docs link from info.json, and every action becomes a ConnectorOperation with a title, description and parameters, even ones no playbook uses yet.
    • Solution packs become SolutionPack nodes that INCLUDES their collections and DEPENDS_ON the packs listed in their dependencies.
    • Documents (pack READMEs and docs, connector references generated from info.json and release notes, widget READMEs) are split into ~1,200-character chunks with 200 characters of overlap. Chunks link with EXPLAINS to the connectors and FortiSOAR concepts they mention.

    5.6 Derived links

    After every load, these links are rebuilt from the graph:

    • Playbook REFERENCES vendor doc: through the connectors it uses (the connector's reference doc), through features its steps use, and through its solution pack's own docs.
    • Collection DOCUMENTED_BY / REFERENCES doc: rolled up from its playbooks, recording which playbooks it came through.
    • Playbook DOCUMENTED_BY internal doc: only for your own runbooks: name matches are approved automatically, and LLM or similarity suggestions wait for review (links approve).

    5.7 Search indexes and embeddings

    Each playbook's summary (name, pack, description, trigger, steps and connectors) and each document chunk is turned into a vector (embedding) and stored in Neo4j vector indexes. Full-text indexes cover names, titles, descriptions and chunk text. Embeddings are cached on disk, so re-loads only embed new or changed text.

    7. How the graph is shown in the app

    Colours and shapes

    Every node is a circle; colour and size tell the types apart. The same legend appears under each graph, and clicking a legend chip hides or shows that type everywhere.

    Home

    • Ecosystem map (large graphs): solution packs in the centre and the connectors their playbooks use on the outer ring, with dashed edges for pack dependencies. Thousands of individual playbooks can't be drawn readably, so this view is used once there are more than 300.
    • Alerts → Playbooks and Incidents → Playbooks: the module in the centre; the playbooks triggered by it (solid amber edges, labelled with the trigger type) or creating, updating or finding its records (dotted ACTS_ON edges); then the child playbooks they call; and the connectors all of them use on the outside.
    • All playbooks: collections in the centre, then playbooks, modules and connectors (the default for small graphs).
    • Nodes fly out from the centre and fade in ring by ring. Double-click any node to pull its direct links into a ring around it, with outward-pointing labels and everything else faded. Double-click again, click the background or press Esc to restore.

    Catalog

    Each tab lists one node type with counts that come from the graph (steps, callers, runbooks, connectors, samples…). Detail panels show the node's neighbourhood as links: a playbook shows its steps (with connector operations and ⚠ secret flags), calls, callers, runbooks and vendor docs; a connector shows each action and the playbooks and steps that use it; a document shows its full text and what links to it. Large tabs render 300 rows at a time; search or filter to narrow them.

    Graph panel (Chat)

    Shows the neighbourhood of the playbooks an answer cites: collection, trigger modules, steps (dashed NEXT edges), connector operations and connectors, called and calling playbooks, and linked documents. ▶ Play walks through the steps in execution order, in Auto (speed up to 10×) or Manual mode with Prev and Next (or the arrow keys), with a note above the graph explaining each step from its actual arguments.

    Diagrams

    Generated from the graph, never by the language model: a flowchart of the step logic (circles, the trigger as a double circle, branch labels, approvals, child playbooks, secrets outlined in red) and a sequence diagram showing who talks to whom (trigger, then playbook, then each connector, child playbook and analyst). Use ⤢ Expand to view either full screen.

    8. How chat answers are produced

    1. Understand: a follow-up question is rewritten into a standalone question using the conversation, shown as "Interpreted as…".
    2. Search: hybrid retrieval. Vector similarity (embeddings) and keyword full-text search run over playbooks (including matches on their steps, connectors and modules) and document chunks, and the two rankings are merged with reciprocal rank fusion.
    3. Graph: expansion from the hits. Each top playbook brings its trigger, ordered steps, connector operations, callers, callees and docs, and document hits pull in the playbooks linked to them.
    4. Answer: the language model writes the answer from that context only, streaming it back with citations: [C#] for a company playbook, [D#] for an internal doc and [V#] for a vendor or GitHub doc. Every playbook the answer cites or names gets a diagram card.
    Listing questions ("which playbooks…") see only the top search results, so they can miss items in a large graph. Use the Catalog filters for complete lists.

    10. Limitations and known gaps

    • Only content published on GitHub is included. Packs that ship their playbooks only through Content Hub appear through their docs alone, and connectors without a public repo (for example some firewall connectors) have no description or action list.
    • Calls to playbooks that aren't loaded show as placeholder nodes ("unresolved:<uuid>").
    • Step types and triggers are inferred from arguments, so unusual custom steps may show as a generic "action".
    • Chat needs the language model's quota. On Gemini's free tier, daily request and embedding limits apply.

    11. Glossary

    PlaybookA FortiSOAR workflow: a trigger plus steps.
    CollectionA folder of playbooks.
    Solution packA Content Hub bundle of collections, modules and docs for a use case.
    ConnectorAn integration with an external product installed in FortiSOAR, e.g. virustotal.
    Connector operationOne action a connector offers, e.g. virustotal.get_file_reputation. A playbook step USES an operation, which is OF a connector. Operations appear in the Chat graph panel (small light-teal circles between steps and connectors), in each connector's Catalog page under "Operations and where they're used", and on playbook steps. The Home ecosystem map shows connectors only.
    ModuleA FortiSOAR record type (alerts, incidents, indicators…).
    ChunkA passage of a document used for search.
    EmbeddingA numeric vector of text used for similarity search.
    RRFReciprocal rank fusion, which merges the vector and keyword rankings.
    PlaceholderA node for a called playbook that isn't loaded.
